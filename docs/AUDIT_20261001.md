## Findings requiring action

### Pending highlight recovery can silently abandon valid work

**P1, confirmed source defect; no new runtime failure injection.** `android/app/src/main/java/com/reader/app/data/ReadingSession.kt:40` scans only `.json` journals. Lines 51–69 place JSON decoding, `saveDraft` and file deletion under one catch; every non-cancellation error renames the journal to `.json.bad`. A temporary Room/write failure on a valid pending highlight is therefore treated as corrupt input, silently removed from future automatic replay. The bytes remain in a sidecar; this is recovery abandonment, not proven physical deletion.

`ReaderApp.kt` instantiates this path at application startup with `HighlightRepository.saveSelection`. Existing `ReadingSessionTest` verifies retry of in-memory commands but does not cover this durable replay branch.

Required result: distinguish invalid input from transient persistence/cleanup failure; retain valid work for explicit retry/restart; expose unresolved recovery without blocking every later operation indefinitely; preserve identity/revision ordering. Do not blindly replay all old `.bad` files or discard them.

### Chrome safety does not cover a response becoming editable

**P1 for the reported pollution risk, source gap confirmed; current live recurrence unmeasured.** `chrome/src/content/capture.ts:149` can remove a control from an editable response only when reconciliation visits it. The observer at lines 274–275 watches `aria-busy` and `data-is-streaming`, not editability/role/editor-class changes; line 263 ignores editable-target mutations. A previously mounted response can become editable and retain the injected control.

The five-second cooldown at lines 174–175 has no scheduled follow-up. One framework removal followed by a settled DOM can therefore leave no control until a later unrelated mutation. Global observer suppression at lines 206–211 and 239 can also drop provider changes during insertion. These are deterministic lifecycle gaps, not a reason to guess more provider selectors.

Required result: no controls or text changes inside editing surfaces; bounded, eventual reconciliation on a supported read-only response; one control per response; explicit toolbar/selection fallback when safe placement is unknown. Never remove ordinary “Reader” text from a user's saved content as an automatic cleanup.

The two September 30 failing tests likely have a **fixture defect**: `inline-mount.test.ts:37,49` creates a separate JSDOM window, while `adapters.ts:62` checks ambient `instanceof Element`. The foreign-window elements fail that check. Fresh execution was blocked by missing tooling, so this is a strongly supported diagnosis rather than a new passing test. The fixture also does not execute the production observer. Fix the fixture and test actual transitions before changing production behavior to satisfy it.

### Speech Pause can be overridden by a loading completion

**P2, source control-flow defect.** `TtsNarrator.kt:91–94` pauses the controller but does not change the pending playback intention/session. Asynchronous initial/next-section loads unconditionally call `controller.play()` at lines 75 and 154. Pause or audio-focus loss while loading can therefore be followed by unwanted playback. Existing stale-stop handling does not establish stale-pause handling.

Test with a deliberately suspended section loader: Pause, release the load, verify no speech; explicit Play must resume correctly. Repeat at a section boundary and with audio-focus loss. Ordinary UI Listen already pauses before starting another article, so the separate concern about old audio during `start()` is a latent service-boundary risk, not a demonstrated normal-UI regression.

### Ordinary article exit pauses service-owned listening

**P2, source/callsite contradiction.** `PreparedReaderScreen.kt:417` routes Back through `transition()`, which calls `onPauseAudio()` at line 383. `MainActivity.kt:692` binds that to `ttsClient.pause()`, despite lines 677–680 explicitly intending narration to continue with controls in the library. The shared transition also affects other article actions.

Separate persistence transitions from audio policy. Back to the library should preserve listening; entering Speed should pause it; deletion/explicit Stop should follow a deliberate policy. Verify the real MediaSession path, not only an isolated narrator.

### Settled pen highlights leave native selection handles

**P2, historically observed physical defect; source unchanged.** The September 14 TCL image `artifacts/trial-fixes-20260914/tcl-qa-5-highlight-settled-monochrome-dark.png` visibly retains selection handles while showing “Undo highlight.” I inspected this historical image during the audit. The current `NativeArticleView.kt:729` settlement path still relies on session identity when clearing after acknowledgement.

The prior proposed gesture-generation fix is a hypothesis, not a mandate. Preserve stale-ack protection: successful save may clear the completed gesture, never a newer pointer gesture. Verify one row/final range, cancellation, a delayed acknowledgement and a second gesture. Native handles require direct observation on the resulting build.

### Speed progress is only durably saved on explicit exit

**P2, source persistence gap; process-loss scenario unmeasured.** `RsvpScreen.kt:54` keeps index in `rememberSaveable`; ON_STOP at line 61 only pauses. Durable progress is offered/flushed by the explicit exit callback at `MainActivity.kt:743–748`. Android saved-state restoration mitigates ordinary recreation, but it is not a durable reading checkpoint after loss of saved state/task removal. Add bounded progress checkpoints without per-word database writes. Defer this behind the higher-priority repairs if tonight's budget is tight.

### The extension can report an incorrect recovery state

**P2, secondary to the capture safety repair.** `service-worker.ts:511–515` returns a terminal `settled` result for an existing capture identity, while `capture.ts:77` ignores it and may display waiting/unpaired. `service-worker.ts:1278,1286` also substitutes empty arrays for storage-read errors and returns healthy status. This can mislead the user about saved work; it is not proof of data deletion. Test terminal-ID retries and IndexedDB failure, then show honest states without recreating transfers or discarding rows.

### Documentation overstates and understates the implemented speech behavior

`AndroidTtsEngine.kt:19,50–59` explicitly selects `com.google.android.tts`; README and INSTALL say system-default. Correct those claims to the later owner decision. `docs/STATUS.md` says speech cannot continue across parts, but `TtsNarrator.kt:131–155` implements following-section loading and existing tests cover it. Describe it as implemented with lifecycle fixes/validation still needed; native cross-part selection remains a separate limitation.

The expanded Appearance screenshot `s23-qa-11-appearance-expanded-bottom.png` confirms the historical dismissal/header issue. Keep that small usability repair separate from a broad visual redesign. Neither this screenshot nor NXTPAPER screenshots establish electrophoretic refresh quality or current accessibility compliance.

One additional integrity hardening item belongs in the later backlog: `HighlightRepository.kt:93–101` turns a malformed persisted Review envelope into an empty round, and resume/focus can subsequently overwrite it. Highlight rows survive, but round continuity can be lost. A rare corruption/future-format trigger was not reproduced. Preserve undecodable state and expose recovery before replacement when this item is taken up; it is not a reason to expand tonight's mandatory scope.

## Security and architecture assessment

The appropriate architecture remains local reading plus encrypted transport. Current source has authenticated pairing, strict schemas/signatures, resource bounds, channel generation/lease checks, durable capture identities and receipts, and queue removal after authenticated device storage acknowledgement. These are substantial foundations worth preserving.

The current [NIP-59 specification](https://github.com/nostr-protocol/nips/blob/master/59.md) distinguishes persistent kind 1059 wrapping from ephemeral 21059. Reader's asynchronous/offline use of persistent envelopes is directionally appropriate. [NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md) does not provide forward secrecy. Neither specification validates Reader's implementation by itself. This audit did not perform independent cryptographic verification or new relay interoperability probes.

MV3 worker termination is an expected lifecycle condition, so persisted outbox/retry state remains necessary; current [Chrome lifecycle guidance](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) supports testing that boundary. A foreground receipt does not establish background, reboot, Doze or statistical reliability.

Fresh `npm audit --package-lock-only --ignore-scripts --json` returned **one LOW advisory**, zero moderate/high/critical advisories: DOMPurify 3.4.14 is covered by [GHSA-p98j-92pf-mc4p](https://github.com/advisories/GHSA-p98j-92pf-mc4p); the stated fix is 3.4.16. The advisory requires `IN_PLACE` plus a node-removing after-sanitize hook. Reader's inspected call at `pipeline.ts:153` sanitizes a string; neither that option nor such a hook was found. Package exposure is confirmed; a reachable exploit in Reader is not demonstrated. Patch narrowly and rerun extraction/build checks. No fresh Android/Rust/Swift advisory audit was completed.

Keep privacy claims precise: local content and endpoint keys remain vulnerable to endpoint compromise; relay operators see metadata; expiration is not guaranteed erasure; a speech voice may use its own network service. An export is readable and checksum-verifiable, but it is not a restorable full backup. Restorable recovery is the most consequential later feature gap for a long-lived personal library.

Rust and Swift are reference packages, not a production shared runtime. Mac is not a finished app; iOS is unimplemented. Do not spend tonight on UniFFI, a new backend, AI summaries, semantic search or new provider integrations. No evidence from this audit justifies adding an AI dependency to deterministic storage, UI or transport repairs.

## A bounded definition of excellence

For tonight, success is a reviewable candidate that preserves pending passages, never intrudes into provider editors, obeys speech controls, settles highlighting correctly, and has evidence tied to its exact source and packages. One ordinary capture-to-receipt flow and one short recovery scenario are enough to detect integration mistakes; they do not certify a reliability percentage.

After that candidate is accepted, prioritize: restorable library recovery; a small real-life interruption matrix; accessibility and large-text reading comfort on actual target devices; honest supported-provider qualification; measured cold-open/large-library performance; release/update signing and migration discipline. Set measurements before claiming improvement. Keep broader platform expansion last.

Suggested planning envelope, not an estimate guarantee: 4–6 hours for the core work with dependencies and test access available. At roughly 90 minutes, drop stretch items if reproduction or environment repair is consuming the session. If only two hours are available, finish the journal and Chrome safety work and leave an exact handoff. Do not replace unfinished acceptance with another sweeping completion report.
